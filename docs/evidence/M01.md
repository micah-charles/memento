# M01 evidence — Windows shell and local storage

**Status:** BLOCKED at the M01 gate
**Date:** 2026-09-13
**Starting checkpoint:** `82cbcccec1250f0addaa09451d3b20d4cbeadce3`
**Implementation commit:** `6419f48` (`feat: establish M01 local storage foundation`)

## Scope

This slice implements the local archive foundation and a minimal WinUI shell. It does not capture audio or call a cloud provider.

## Environment

- Windows 10.0.19045
- .NET SDK 10.0.400
- Windows App SDK 2.4.0 (current stable release checked against Microsoft documentation on 2026-09-13)
- Self-contained Windows App SDK deployment enabled for the unpackaged executable
- SQLite through `Microsoft.Data.Sqlite` 10.0.0 with `SQLitePCLRaw.lib.e_sqlite3` pinned to 2.1.13 because the transitive 2.1.11 package was reported vulnerable

## Implementation

- `src/Memento.App`: minimal WinUI 3 app shell with large readable status text
- `src/Memento.Core`: SQLite archive, schema migrations, FK/WAL setup, stable IDs and UTC timestamps
- Tables: `sessions`, `turns`, `consent_events`, `sources`, and `schema_migrations`
- `ArchiveRepository` persists Session, Turn, Consent Event, and Source metadata placeholder records
- Database directories are created under the caller-supplied local application data path
- App startup initializes `%LOCALAPPDATA%\\MEMENTO\\data\\memory.db` before activating the window

## Programmatic verification

The initial framework-dependent executable showed a Windows error window titled `Memento.App.exe - This application could not be started` and did not create the database. After enabling self-contained Windows App SDK deployment, a direct executable launch remained alive for 5 seconds with a `MEMENTO` main window title and created `%LOCALAPPDATA%\\MEMENTO\\data\\memory.db` (53,248 bytes). This verifies process startup and startup database initialization programmatically; it is not a visual inspection of the window contents.
